## 2. 시스템 구성

### 2.1 구성도

```
 [스마트폰·PC 브라우저]
        │  HTTPS
        ▼
 ┌──────────────────────┐        ┌───────────────────────────────────┐
 │ Cloudflare Pages      │        │ Supabase (dev / prod 프로젝트 2개)  │
 │  React SPA 정적 파일   │        │                                   │
 │  (HTML·JS·CSS)        │        │  Auth ── 이메일 6자리 코드 로그인    │
 └──────────────────────┘        │  REST API (PostgREST)              │
        │ 페이지 로드 후            │    └ PostgreSQL + RLS 정책          │
        │ 브라우저가 직접 호출       │  DB 함수(RPC) ── 트랜잭션 처리      │
        └──────────────────────▶  │  Storage ── 레시피 사진            │
     supabase-js + publishable key └───────────────────────────────────┘
```

- 별도 백엔드 서버는 두지 않는다. 브라우저가 supabase-js로 Supabase에 직접 요청하고, 데이터 보호는 DB의 RLS 정책이 맡는다.
- 여러 테이블을 함께 바꿔야 하는 작업(가져오기, 전체 삭제, 식단 저장에 따른 음식 상태 재계산)은 DB 함수로 만들어 트랜잭션 안에서 처리한다.

### 2.2 환경

| 환경 | 프론트엔드 | Supabase | 데이터 |
| --- | --- | --- | --- |
| 로컬 개발 | 개발자 PC (`npm run dev`) | dev 프로젝트 | 가명 테스트 데이터 |
| 운영 | Cloudflare Pages | prod 프로젝트 | 실제 기록 |

- 로컬에 Docker로 Supabase를 띄우지 않는다 (E3 결정).
- dev와 prod는 같은 마이그레이션 파일로 같은 스키마를 유지한다.

### 4.3 환경변수

| 이름 | 용도 | 위치 |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | Supabase 프로젝트 주소 | `.env.local`(dev), Cloudflare Pages 설정(prod) |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | 브라우저용 공개 키 (`sb_publishable_`로 시작). 기존 anon key의 후속 키 | 위와 같음 |

- `VITE_`로 시작하는 값은 빌드 결과물에 포함되어 누구나 볼 수 있다. 공개되어도 되는 값만 이 이름을 쓴다.
- **Secret key(`sb_secret_`, 기존 service role key)는 어떤 환경변수에도 넣지 않는다.** RLS를 우회하는 관리자 키다. 관리 작업은 Supabase 대시보드나 CLI에서 직접 한다.
- 테스트 계정 정보는 `.env.test.local`(예시: `.env.test.example`)에 둔다. dev 프로젝트 계정만 넣는다.
- 허용 이메일은 코드나 환경변수가 아니라 Supabase Auth 사용자 목록으로 관리한다 (7.2).

### 4.4 Git과 작업 흐름

- 작업마다 브랜치를 만든다: `feat/…`, `fix/…`, `docs/…`, `chore/…`
- PR로 `main`에 병합한다. PR마다 CI(9.4)가 통과해야 한다.
- 커밋 메시지: `feat: 수면 입력 화면 추가`처럼 접두어 + 한국어 설명

## 5. 데이터베이스 설계

### 5.1 공통 규칙

| 항목 | 규칙 |
| --- | --- |
| 이름 | 테이블·컬럼은 snake_case (`owner_id`, `created_at`). 화면 코드에서는 생성된 타입을 그대로 사용 |
| ID | `uuid`, 기본값 `gen_random_uuid()` |
| 소유자 | 모든 테이블에 `owner_id uuid not null default auth.uid()`, `auth.users` 참조, 사용자 삭제 시 함께 삭제 |
| 시각 | `created_at`, `updated_at` (`timestamptz`, 기본값 `now()`). `updated_at`은 트리거로 갱신 |
| 날짜 | 기록 날짜는 `date`. 기기 기준 날짜를 그대로 저장 |
| 수면 시각 | `timestamp` (시간대 없음). 기기에서 본 벽시계 시각을 그대로 저장. 시간대 기준이 "기기의 현재 시각"(PRD)이므로 변환하지 않음 |
| 인덱스 | 목록 조회용 `(owner_id, date desc)` |
| 검증 | 화면 검증과 같은 규칙을 CHECK 제약과 트리거로 DB에도 둔다 (FR-COM-13) |

### 5.4 서버의 날짜 검증

- 서버는 기기의 시간대를 모른다. DB는 `date <= (현재 UTC 날짜 + 1일)`까지만 허용하고, "오늘 이후 금지"의 정확한 판단은 화면에서 한다 (T10).
- 생년월일 이전 날짜 금지(BR-02)는 `children.birth_date`와 비교하는 트리거로 검증한다.

## 6. 접근 제어

### 6.1 RLS 정책

- 모든 테이블에 RLS를 켠다. RLS가 꺼진 테이블이 생기지 않도록 마이그레이션 리뷰 체크리스트에 넣는다.
- 정책은 테이블마다 같은 형태로 둔다.

```sql
-- 예시: milestones
alter table milestones enable row level security;

create policy "본인 데이터만 조회" on milestones
  for select using (owner_id = auth.uid());
create policy "본인 데이터만 추가" on milestones
  for insert with check (owner_id = auth.uid());
create policy "본인 데이터만 수정" on milestones
  for update using (owner_id = auth.uid()) with check (owner_id = auth.uid());
create policy "본인 데이터만 삭제" on milestones
  for delete using (owner_id = auth.uid());
```

- 로그인하지 않은 요청(anon 역할)은 어떤 테이블도 읽거나 쓸 수 없다.

### 6.2 DB 함수의 권한

- DB 함수는 기본적으로 `security invoker`(호출한 사용자 권한)로 만들어 RLS가 그대로 적용되게 한다.
- `security definer`가 꼭 필요한 함수는 함수 안에서 `auth.uid()`로 대상을 제한하고, `search_path`를 고정한다. 해당 함수는 PR에서 따로 표시해 리뷰한다.

### 6.3 Storage (레시피 사진)

- 비공개 버킷 `recipe-photos`. 파일 경로는 `{owner_id}/{photo_id}.jpg`
- Storage 정책: 경로의 첫 폴더가 `auth.uid()`와 같을 때만 읽기·쓰기·삭제 허용
- 화면에는 만료 시간 1시간짜리 서명 URL로 표시한다. 공개 URL은 쓰지 않는다 (PRD 7장).
- 업로드 순서: 브라우저에서 리사이즈·JPEG 압축 → Storage 업로드 → `photos` 행 추가 → 레시피에 연결. 중간에 실패하면 올라간 파일을 지운다.
- HEIC 사진은 브라우저마다 지원이 달라 변환 라이브러리가 필요할 수 있다 `[확인 C8]`.
- 사진 교체·삭제·레시피 삭제 시 Storage 파일을 먼저 지우고 DB 행을 지운다. 파일 삭제에 실패해 남는 파일은 전체 삭제 시 함께 정리된다.

## 7. 인증

### 7.1 로그인 방식 (FR-AUTH-01~06)

| 항목 | 설정 |
| --- | --- |
| 방식 | Supabase Auth 이메일 OTP (6자리 코드) |
| 회원가입 | Supabase 대시보드에서 "새 사용자 가입 허용"을 끈다 |
| 코드 요청 | `signInWithOtp({ email, options: { shouldCreateUser: false } })` |
| 코드 확인 | `verifyOtp({ email, token, type: 'email' })` |
| 메일 템플릿 | 대시보드의 **Magic link or OTP** 템플릿에 `{{ .Token }}`을 넣어 코드가 보이게 수정. **템플릿은 외부 메일(Custom SMTP)을 연결해야 수정할 수 있다** (C1 확인 완료) |
| 메일 발송 | Gmail SMTP (`smtp.gmail.com:587`). 앱 전용 발송 Gmail 계정을 쓰고, 그 계정의 앱 비밀번호는 Supabase SMTP 설정에만 저장한다 (저장소·환경변수에 넣지 않음) |
| 코드 길이 | **6자리** (Supabase 기본값 8자리에서 변경, Email OTP Length) |
| 코드 유효 시간·재발송 제한 | 기본 유효 시간 1시간을 **10분(600초)**으로 줄임. 같은 사용자의 재요청은 60초 간격(기본값). 코드 검증은 IP당 5분에 30회까지 (C2 확인 완료). 유효 시간 설정은 초대·이메일 변경 링크에도 함께 적용됨 |
| 세션 저장 | supabase-js 기본값(브라우저 localStorage) |

### 7.2 허용 이메일 관리

- dev, prod 프로젝트마다 대시보드에서 사용자 1명을 미리 등록한다. 이 목록이 곧 허용 이메일이다.
- 등록되지 않은 이메일은 `shouldCreateUser: false` 때문에 코드가 발송되지 않는다. 화면은 오류 응답을 받아도 같은 문구를 표시한다 (FR-AUTH-02).
- 기본 메일 발송 서비스는 **프로젝트당 시간당 2통**까지만 보내고 템플릿도 수정할 수 없어, Gmail SMTP를 연결했다 (C3 확인 완료). 외부 메일을 연결한 뒤에는 Authentication → Rate Limits에서 발송 한도를 정할 수 있다. 자동 테스트는 이메일을 쓰지 않는 방식(9.3~9.4)으로 한다.

## 8. 서버 로직 (DB 함수)

### 8.1 공통

| 함수 | 역할 | 관련 요구사항 |
| --- | --- | --- |
| `export_backup()` | 본인 데이터 전체(성장·식사 기록)를 JSON 1개로 반환. `schema_version`, `exported_at` 포함. 레시피 사진은 경로만 넣고 파일은 제외 | FR-SET-02, FR-SET-09 |
| `import_backup(payload jsonb)` | 버전·형식·필수값 검사 → 본인 데이터 전체 삭제 → 파일 내용 입력. 한 트랜잭션이라 중간에 실패하면 모두 취소됨 | FR-SET-03~05, R23 |
| `delete_all_data()` | 본인의 모든 테이블 데이터 삭제 (아이 정보 포함). 로그인 계정은 남김 | FR-SET-06~07 |

- `schema_version`은 정수로 시작한다 (MVP-1 = 1). 마이그레이션으로 백업 형식이 바뀌면 올린다.
- 가져올 때 파일 안의 `owner_id`는 무시하고 현재 사용자로 바꿔 넣는다. 다른 계정 데이터를 넣을 수 없게 하기 위해서다.
- 전체 삭제 시 Storage 사진도 지워야 한다. Storage 파일은 SQL로 직접 지우지 않고, 화면에서 본인 폴더(`{owner_id}/`)의 파일을 Storage API로 지운 뒤 `delete_all_data()`를 호출한다.

### 8.2 식사 기록

| 함수 | 역할 | 관련 요구사항 |
| --- | --- | --- |
| `add_food(name, food_group, memo, already_tried, first_tried_date)` | 음식 추가. "이미 먹어 봤어요"면 `manual_tried`와 상태 먹어봄으로 저장 | FR-FOOD-04~05, BR-17 |

| `delete_meal_entry(id)` | 칸 삭제 + 재계산 | FR-MEAL-13 |
| `set_food_caution(food_id, on, reaction_date, symptom_note, check_note, reason)` | 알러지·주의 지정·해제 + 이력 | FR-FOOD-11~12 |
| `clear_caution_tag(food_id, reason)` | "주의" 태그 해제 + 이력 | FR-FOOD-13 |

**음식 상태 재계산 (내부 함수 `recalc_food`)**

1. `eaten_min` = 그 음식이 담긴 "먹음" 칸의 가장 이른 날짜
2. `first_tried_date` = `eaten_min`과 `manual_first_tried_date` 중 이른 날 (둘 다 없으면 null)
3. 상태 전환은 기능요구사항서 BR-11 표를 따른다.
   - 아직 안 먹어봄 → 먹어봄: "먹음" 기록이 생기면 (이력 없음)
   - 알러지·주의 → 먹어봄 + 주의 태그: `caution_since` 이후 날짜의 "먹음" 칸이 생기면 (이력: `meal_entry`)
   - 먹어봄 + 주의 태그 → 알러지·주의: `caution_since` 이후 날짜의 "먹음" 칸이 모두 없어지면 (이력: `revert`)
   - 먹어봄 → 아직 안 먹어봄: "먹음" 기록이 모두 없어지고 `manual_tried`도 false면 (이력 없음)
4. 식단 함수들은 한 트랜잭션 안에서 칸 저장과 재계산, 이력 기록을 함께 처리한다.

**함수 권한**

- 8.2 함수는 음식 상태 컬럼을 바꿔야 해서 `security definer`로 만든다 (D10). 함수 안에서 모든 조회·수정을 `owner_id = auth.uid()`로 제한하고 `search_path`를 고정한다 (6.2).

### 9.3 E2E 테스트 (Playwright)

- 대상: PRD 8장 MVP-1 완료 기준을 시나리오로 옮긴 것
- 실행 환경: dev 프로젝트, 가명 데이터
- 로그인 처리: 이메일 코드를 자동으로 받을 수 없으므로, dev 프로젝트의 테스트 계정 A로 **비밀번호 로그인**을 한 뒤 시나리오를 실행한다 (D3). 계정 정보는 로컬 PC의 `.env.test.local`에만 두고 CI에는 넣지 않는다. Secret key는 쓰지 않는다.
- 처음에는 로컬에서 수동 실행한다. CI 자동 실행은 MVP-1 완료 후 검토한다.

### 9.4 접근 제어 테스트

- dev 프로젝트에 테스트 계정 2개(A, B)를 두고 비밀번호로 로그인한다. A로 만든 데이터를 B가 조회·수정·삭제할 수 없는지, 로그인하지 않은 요청이 거부되는지 Vitest 통합 테스트로 확인한다.
- 새 테이블을 추가하는 PR에는 이 테스트를 함께 추가한다.

### 9.5 CI (GitHub Actions)

| 시점 | 실행 |
| --- | --- |
| PR 생성·갱신 | 린트, 타입 검사, 단위·컴포넌트 테스트, 빌드 |
| main 병합 | 위와 같음 (Cloudflare Pages 배포는 Pages가 따로 수행) |

- 공개 저장소는 GitHub 호스트 러너가 무료다.
- CI에는 Supabase 키를 넣지 않는다. 단위·컴포넌트 테스트는 Supabase에 연결하지 않고 실행되어야 한다.

### 10.2 보안 설정

- `.gitignore`에 `.env*.local`을 넣고, 공개 저장소이므로 첫 커밋 전에 확인한다.
