### 1.2 범위

| 구분 | 작성 수준 |
| --- | --- |
| MVP-1 (성장 기록, 식사 기록, 공통) | 상세 |

### 1.3 기준 문서

- `PRD.md` v1.2, `docs/기능요구사항서.md` v1.1
- 이 문서에서 기능 동작을 새로 정하지 않는다. 기술적인 이유로 기능 변경이 필요하면 11장에 올려 승인을 받는다.

## 2. 시스템 구성

### 2.1 구성도

```
 [스마트폰·PC 브라우저]
        │  HTTPS
        ▼
 ┌──────────────────────┐        ┌───────────────────────────────────┐
 │ Cloudflare Pages      │        │ Supabase (dev / prod 프로젝트 2개)  │
 │  React SPA 정적 파일   │        │                                   │
 │  (HTML·JS·CSS)        │        │  Auth ── 이메일 6자리 코드 로그인    │
 └──────────────────────┘        │  REST API (PostgREST)              │
        │ 페이지 로드 후            │    └ PostgreSQL + RLS 정책          │
        │ 브라우저가 직접 호출       │  DB 함수(RPC) ── 트랜잭션 처리      │
        └──────────────────────▶  │  Storage ── 레시피 사진            │
     supabase-js + publishable key └───────────────────────────────────┘
```

- 별도 백엔드 서버는 두지 않는다. 브라우저가 supabase-js로 Supabase에 직접 요청하고, 데이터 보호는 DB의 RLS 정책이 맡는다.
- 여러 테이블을 함께 바꿔야 하는 작업(가져오기, 전체 삭제, 식단 저장에 따른 음식 상태 재계산)은 DB 함수로 만들어 트랜잭션 안에서 처리한다.

### 2.2 환경

| 환경 | 프론트엔드 | Supabase | 데이터 |
| --- | --- | --- | --- |
| 로컬 개발 | 개발자 PC (`npm run dev`) | dev 프로젝트 | 가명 테스트 데이터 |
| 운영 | Cloudflare Pages | prod 프로젝트 | 실제 기록 |

- 로컬에 Docker로 Supabase를 띄우지 않는다 (E3 결정).
- dev와 prod는 같은 마이그레이션 파일로 같은 스키마를 유지한다.

## 3. 기술 스택

| 영역 | 선택 | 용도 |

| UI | Tailwind CSS v4 + shadcn/ui(Radix) | 모바일 화면, 확인 창·탭 등 접근성 기본 컴포넌트. 디자인 값은 `src/index.css` 토큰 (T-05) |

| CI | GitHub Actions | PR 검사 |

- `features/` 안의 코드는 다른 기능 폴더를 직접 참조하지 않는다. 공통 로직은 `domain/`이나 `lib/`로 옮긴다. 여러 화면이 함께 쓰는 서버 데이터(로그인 상태, 아이 정보, 발달 기록, 키·몸무게, 수면, 음식)도 `lib/`에 둔다.

**주간 식단 화면 구현 (T-42·T-43·T-44)**

- `src/domain/mealWeek.ts`: 기기 시간대의 월요일~일요일과 기간 이름을 계산한다. 잘못된 주소 날짜는 이번 주로 해석한다.
- `src/lib/mealApi.ts`·`useMeals.ts`·`mealTypes.ts`: 주의 시작일~종료일만 조회하고, 이름 스냅샷을 순서대로 표시한다. Query key는 `["meals", 주 시작일]`이다.
- `/meals/week?week=YYYY-MM-DD`: 이전·다음 주를 주소에 남긴다. 모바일에서 이번 주는 오늘 카드, 다른 주는 월요일 카드를 먼저 보여 준다. 요일 칩과 스와이프의 선택 상태가 함께 갱신된다.

- `mealApi.ts`는 주 단위 목록 외에 단건 ID 조회, `save_meal_entry`·`delete_meal_entry` 호출과 서버 오류 분류를 담당한다. 화면은 식단 테이블을 직접 쓰지 않는다.
- 새 칸 주소는 `?record=new&date=YYYY-MM-DD&meal=breakfast`이며 수정은 `?record=UUID`다. 기존 `week`는 유지한다. `useSheetParam`이 날짜·끼니 매개변수도 관리하고, 직접 진입한 시트를 닫으면 해당 매개변수만 제거한다. 다른 주의 ID 주소도 단건 조회로 연다.
- 저장·삭제 후 식단과 음식 Query를 갱신한다. 중복 저장이 거부되면 입력을 유지하면서 주간 목록을 갱신해 기존 칸을 다시 열 수 있게 한다.
- `mealSchema.ts`는 음식·레시피 합계 1개 이상, 메모 500자, 기기 기준 미래 먹음 금지, 생년월일 이전 금지를 검사한다. 새 음식은 식품군만 고르고 `add_food`로 아직 안 먹어봄 상태로 만든다.
- `MealRecipePicker`는 전달받은 목록에서 검색·선택·제외한다. T-51에서 본인 레시피 목록과 재료를 조회해 공급한다. 선택 UI는 컴포넌트 테스트로 검증하고, 저장된 식단의 레시피 ID·이름(삭제되어 ID가 null인 경우 포함)은 보존한다. 조회 중·실패를 빈 목록과 구분하며 실패 시 재시도할 수 있다.

- `setMealEaten`·`useSetMealEaten`: 전용 RPC로 체크만 바꾸고 식단·음식 Query를 함께 갱신한다. 성공 응답 전에는 기존 체크를 유지하고 처리 중 중복 요청·식단 편집을 막는다. 미래 칸은 기기 날짜 기준으로 체크를 막는다. 실패하면 기존 상태와 재시도 안내를 유지한다.
- `mealCautionFoods`: 현재 음식 ID의 알러지·주의 상태 또는 주의 태그로 판단하고 중복 재료를 한 번만 경고한다. 이름만 남은 삭제된 음식은 경고 대상에서 제외한다. `useMealRecipes`가 실제 `MealRecipeOption.ingredients`를 공급해 선택·체크·복사에 같은 경고를 적용한다.
- 주의 음식은 계획 칸에도 배지를 붙인다. 입력 상단 경고와 저장 확인 창을 두고, 표에서 먹음으로 바꿀 때도 확인을 받는다. 확인 취소는 입력·체크를 보존한다. 주의 정보를 아직 못 읽었거나 불러오기 실패 상태면 저장·체크 켜기를 막고 다시 불러오게 한다. 재시도도 현재 주의 정보를 다시 확인한다.
- `notifyMealSaved`: 저장·체크 RPC의 첫 시도 목록이 있을 때 이름과 조사에 맞춰 한 번 알리고, 없으면 일반 저장 알림만 표시한다. T-51부터 "타임라인에 남겼어요"까지 표시한다.
- PC 7열 표는 카드당 최소 128px로 체크·배지가 잘리지 않게 하고 좁은 창에서는 표 안에서만 가로 스크롤한다. 본문 최대 폭 1,280px은 유지한다.

- `moveMealEntry`·`useMoveMeal`: T-41 RPC를 호출하고 식단·음식 Query를 갱신한다. 충돌·없는 기록 오류는 목록을 새로 불러오고 입력을 유지한다.
- `MealMoveSheet`: 날짜(생년월일 이후, 미래 허용)·끼니를 고른다. 기기 기준 미래로 먹음 식단을 옮길 때 확인 후 `uncheck=true`를 보낸다. 계획은 체크를 켜지 않는다. 처리 중 닫기·중복 실행을 막는다.
- PC는 식단 칸의 손잡이를 끌어 다른 날짜·끼니에 놓는다. 앱 안에서 시작한 식단 ID만 받으며 모바일은 끌기를 막고 같은 이동 메뉴를 쓴다. 미래 드래그도 확인을 받는다. 생년월일 이전 칸으로 놓으면 이동하지 않고 이유를 안내한다. 서버의 같은 22007 코드도 생년월일 이전과 미래 날짜 오류를 구분한다. 실패하면 원래 기록을 유지하고 안내하며, 통신 오류는 재시도할 수 있다.
- 이동 후 목적지의 주와 요일을 보여 준다. 기록이 있는 칸은 DB가 덮어쓰지 않고 거부한다.

**음식 상세 구현 (T-46)**

- `/meals/foods/:id`: 단건 RLS 조회 후 정보·반응·주의 정보·먹은 식단·변경 이력을 표시한다. 목록은 상세로 연결하며 기존 `?record=ID` 수정 주소도 유지한다. 상세의 수정 버튼은 공통 `FoodSheet`를 재사용한다. 뒤로 가면 목록의 상태·식품군·이름 검색(`q`)을 유지한다.
- `foodDetailApi.ts`·`useFoodDetails.ts`: 횟수 집계, 먹은 식단·주의 이력 조회, 반응 저장을 담당한다. Query key는 기존 `foods` 아래에 둬 식단 저장·체크·이동·삭제와 음식 상태 변경 시 함께 무효화된다.
- `food_meal_counts()`는 `security invoker` 읽기 전용 함수다. 본인의 직접 음식 연결 중 `eaten=true`인 식단만 집계하고, 계획·레시피 재료·음식 삭제 후 남은 이름·직접 먹어봄 지정 자체는 세지 않는다. 행 수 제한이 적용된 목록 길이로 횟수를 계산하지 않는다.
- 먹은 식단은 부모 식단에 `meal_entry_foods!inner`와 음식 ID·먹음 필터를 적용해 날짜 내림차순(같은 날짜는 기록 생성 시각, ID)으로 읽는다. 이력은 `changed_at`·ID 내림차순이다. 각각 20개와 다음 페이지 유무 확인용 1개를 조회하고 더 보기로 이어 붙인다.
- `setFoodPreference`는 현재 상태가 `tried`인 본인 행에 `preference` 한 필드만 수정한다. 이름·메모·직접 먹어봄 설정을 다시 보내지 않아 동시에 바뀐 값을 덮어쓰지 않는다. 반응은 자동 식단 섭취량과 분리하며 같은 반응을 다시 누르면 null로 지운다.
- 주의 태그 해제는 기존 RPC·사유 확인 창을 재사용한다. 상세에 현재 주의 정보와 해제 이력에 보존된 반응 날짜·증상·확인 메모를 각각 표시하며, 자동 먹어봄 전환과 주의 상태 복원도 구분한다. 삭제되어 연결이 사라진 식단은 링크를 표시하지 않는다.
- 로딩·없는 기록·조회 실패·반응 저장 실패·다음 페이지 실패를 처리하고 이미 읽은 내용은 유지한다.

**한 끼 식단 복사 (T-53, FR-MEAL-16)**

- 각 식단의 복사 버튼에서 `MealMoveSheet`의 copy 모드를 연다. 이동과 날짜·끼니 입력·검증·오류 처리를 공유한다. 기본 날짜는 원본 다음 날이며 원본 음식·레시피·메모를 새 계획으로 가져온다는 안내를 표시한다.
- `copyMealEntry`·`useCopyMeal`은 원본 ID와 대상 날짜·끼니만 보낸다. 먹음·섭취량을 화면에서 복제하지 않는다. 주의 음식 정보를 못 읽었으면 복사를 막고 다시 조회하게 한다. 주의 상태·태그 음식이면 경고 후 [그래도 복사] 확인을 받는다.
- 처리 중 중복 복사·칸 수정·체크·이동과 시트 닫기를 막는다. 충돌·원본 없음·자료 변경·통신 오류는 입력을 유지하고 안내하며, 통신 실패는 재시도할 수 있다. 성공 후 대상 주·요일로 이동하고 식단·음식 Query를 갱신한다.

## 5. 데이터베이스 설계

### 5.1 공통 규칙

| 항목 | 규칙 |
| --- | --- |
| 이름 | 테이블·컬럼은 snake_case (`owner_id`, `created_at`). 화면 코드에서는 생성된 타입을 그대로 사용 |
| ID | `uuid`, 기본값 `gen_random_uuid()` |
| 소유자 | 모든 테이블에 `owner_id uuid not null default auth.uid()`, `auth.users` 참조, 사용자 삭제 시 함께 삭제 |
| 시각 | `created_at`, `updated_at` (`timestamptz`, 기본값 `now()`). `updated_at`은 트리거로 갱신 |
| 날짜 | 기록 날짜는 `date`. 기기 기준 날짜를 그대로 저장 |
| 수면 시각 | `timestamp` (시간대 없음). 기기에서 본 벽시계 시각을 그대로 저장. 시간대 기준이 "기기의 현재 시각"(PRD)이므로 변환하지 않음 |
| 인덱스 | 목록 조회용 `(owner_id, date desc)` |
| 검증 | 화면 검증과 같은 규칙을 CHECK 제약과 트리거로 DB에도 둔다 (FR-COM-13) |

### 5.2 성장 기록·공통 테이블

**body_measures** (키·몸무게, F-05)

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| id, owner_id | uuid | |
| date | date | not null |

- CHECK: `height_cm is not null or weight_kg is not null`
- UNIQUE: `(owner_id, date)` 측정 날짜당 1건 (FR-BODY-06). 위반하면 23505로 거부되고, 화면은 측정 날짜 칸에 "같은 날짜에 측정 기록이 있어요"를 표시한다. 이 제약의 인덱스가 목록 조회(날짜 최신순)도 맡는다.

**milestones** (발달 기록, F-06)

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| id, owner_id | uuid | |
| date | date | not null |
| type | text | not null, `word` / `behavior` / `expression` (2026-10-28: `play`는 `behavior`로 합침, R42) |
| title | text | not null, 1~30자 |
| title_key | text | 생성 컬럼. BR-03 기준으로 정리한 값 (공백 정리, 소문자) |
| memo | text | 500자 이하 |
| created_at, updated_at | timestamptz | |

- 인덱스 `(owner_id, type, title_key)`: DB에서 같은 내용을 찾을 때 사용 (BR-03)
- 비슷한 기록(FR-MS-05)과 같은 내용 확인(FR-MS-06)은 입력 화면이 불러온 발달 기록 목록을 `domain/text.ts`로 비교한다 (title_key와 같은 규칙). 글자를 입력할 때마다 서버에 묻지 않기 위함이다.
- 같은 유형에 같은 내용(같은 `title_key`)은 저장할 수 없다 (FR-MS-06, R41). 트리거 `reject_duplicate_milestone`이 23505로 거부하고, 화면은 내용 칸에 "이미 기록된 내용입니다"(단어는 "이미 말한 단어예요")를 표시한다.
  - unique 인덱스 대신 트리거를 쓰는 이유: 변경 전에 저장된 같은 내용이 남아 있을 수 있고, 그 기록의 날짜·메모 수정은 막지 않기 위함이다. 유형이나 내용을 바꾸지 않은 수정은 검사하지 않는다 (화면과 같은 기준).
  - `title_key`는 생성 컬럼이라 BEFORE 트리거에서 읽을 수 없어 AFTER 트리거로 검사한다.
  - 두 기기에서 같은 내용을 동시에 저장하는 경우까지는 막지 않는다 (개인용 앱).
- 놀이를 행동에 합치는 마이그레이션 (R42): 기존 `play` 기록을 `behavior`로 바꾼 뒤 `type` 제약에서 `play`를 뺀다.
  - 같은 내용의 행동 기록이 이미 있어도 두 기록을 모두 남긴다. 이미 저장된 기록의 유형만 바꾸는 것이므로 이 변경 동안만 검사 트리거(같은 내용, 날짜 범위)를 끄고, 끝나면 다시 켠다. 남은 같은 내용은 R41 이전 기록과 같이 다루며(날짜·메모 수정 가능), 유형별 개수에서는 1개로 센다 (R28).
  - 내보내기 파일(T-29)은 이 변경 뒤에 만들어지므로 `play`가 든 파일은 없다.

**sleep_logs** (수면, F-10)

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| id, owner_id | uuid | |
| date | date | not null, 수면일 |
| bed_time | timestamp | null 허용 |
| wake_time | timestamp | null 허용 |
| naps | jsonb | 기본값 `[]`. `[{ "start": "2026-10-13T10:00", "end": "2026-10-13T11:20" }]` |
| memo | text | 500자 이하 |

- `foods.status`, `caution_tag`, `first_tried_date`, `caution_since`는 화면에서 직접 바꿀 수 없게 컬럼 수정 권한을 막고, 8.2의 DB 함수로만 바꾼다. 이름·식품군·메모·반응은 화면에서 바로 수정한다.
- 권한으로 구현한다 (T-36). Supabase는 새 테이블에 전체 권한을 주므로 테이블 단위 추가·수정 권한을 빼고 다시 준다.
  - `foods`: 조회·삭제는 그대로. 수정은 `name`, `food_group`, `memo`, `preference` 컬럼만 허용한다. 그 밖의 컬럼(상태, 처음 먹은 날, `manual_tried`, 알러지·주의 정보, `is_default`)은 DB 함수로만 바뀐다. 추가도 `add_food()`·`seed_default_foods()`로만 한다.
  - 음식 추가·수정 시트는 "이미 먹어 봤어요"와 반응을 함께 저장하므로 `add_food()`·`update_food()`를 쓴다 (T-37). 음식 상세의 반응 선택은 `preference` 컬럼을 바로 수정한다 (T-46).
  - `food_status_history`: 조회만 허용한다. 이력은 DB 함수가 쓰고, 음식을 지우면 외래 키로 함께 지워진다.
  - 권한이 없는 추가·수정은 42501로 거부된다. RLS 정책은 다른 테이블과 같은 형태로 함께 둔다.

- 서버는 기기의 시간대를 모른다. DB는 `date <= (현재 UTC 날짜 + 1일)`까지만 허용하고, "오늘 이후 금지"의 정확한 판단은 화면에서 한다 (T10).

## 6. 접근 제어

### 6.1 RLS 정책

- 모든 테이블에 RLS를 켠다. RLS가 꺼진 테이블이 생기지 않도록 마이그레이션 리뷰 체크리스트에 넣는다.
- 정책은 테이블마다 같은 형태로 둔다.

```sql
-- 예시: milestones
alter table milestones enable row level security;

create policy "본인 데이터만 조회" on milestones
  for select using (owner_id = auth.uid());
create policy "본인 데이터만 추가" on milestones
  for insert with check (owner_id = auth.uid());
create policy "본인 데이터만 수정" on milestones
  for update using (owner_id = auth.uid()) with check (owner_id = auth.uid());
create policy "본인 데이터만 삭제" on milestones
  for delete using (owner_id = auth.uid());
```

- 로그인하지 않은 요청(anon 역할)은 어떤 테이블도 읽거나 쓸 수 없다.

### 6.2 DB 함수의 권한

- DB 함수는 기본적으로 `security invoker`(호출한 사용자 권한)로 만들어 RLS가 그대로 적용되게 한다.
- `security definer`가 꼭 필요한 함수는 함수 안에서 `auth.uid()`로 대상을 제한하고, `search_path`를 고정한다. 해당 함수는 PR에서 따로 표시해 리뷰한다.

### 6.3 Storage (레시피 사진)

- 비공개 버킷 `recipe-photos`. 파일 경로는 `{owner_id}/{photo_id}.jpg`
- Storage 정책: 경로의 첫 폴더가 `auth.uid()`와 같을 때만 읽기·쓰기·삭제 허용
- 화면에는 만료 시간 1시간짜리 서명 URL로 표시한다. 공개 URL은 쓰지 않는다 (PRD 7장).
- 업로드 순서: 브라우저에서 리사이즈·JPEG 압축 → Storage 업로드 → `photos` 행 추가 → 레시피에 연결. 중간에 실패하면 올라간 파일을 지운다.
- T-48 구현: `prepareRecipePhoto.ts`에서 0바이트·20MiB 초과·JPG/PNG/HEIC 외 실제 헤더를 거부한다. 방향을 반영해 흰 배경에 그린 뒤 긴 변 1,280px 이하·JPEG 품질 0.82로 만든다. 작은 사진은 확대하지 않는다.
- HEIC는 `heic-to@1.6.7/csp`를 지연 로딩하고 내부 Worker로 기기 안에서 변환한다. 외부 변환 서비스로 사진을 보내지 않는다. LGPL-3.0-or-later와 내부 libheif/libde265 소스·빌드 링크 및 라이선스 전문을 `public/THIRD_PARTY_NOTICES.txt`·`public/licenses/`에 둔다. [공식 사용법·라이선스](https://github.com/hoppergee/heic-to).
- C8 검증: 공개 libheif HEIC 샘플과 생성 PNG로 Chrome·WebKit 18에서 JPEG와 1,280px 제한을 확인했다. 현재 macOS 13에서 실행 가능한 WebKit 엔진을 임시 테스트 환경에 설치했으며 프로젝트 의존성에는 넣지 않는다. T-50 입력 화면의 JPG·PNG·HEIC 파일 선택·저장·교체·삭제를 데스크톱 브라우저에서 확인한다. 실제 사용자 iPhone의 사진 보관함 선택은 기기에서 수동 확인이 남아 있다.
- CSP 헤더를 추가하는 T-34에서는 HEIC 내부 Worker에 `worker-src blob:` 허용이 필요하다. CSP용 디코더이므로 `unsafe-eval`은 사용하지 않는다.
- 버킷은 비공개·JPEG만·20MiB 제한이며, 본인 UUID/사진 UUID.jpg 경로에 SELECT·INSERT·DELETE만 허용한다. UPDATE 정책이 없어 upsert 덮어쓰기는 거부한다. [공식 Storage 권한 문서](https://supabase.com/docs/guides/storage/security/access-control).
- `recipePhotoApi.ts`: 변환 파일을 `upsert=false`로 새 경로에 올린 뒤 photos 행을 저장한다. 메타데이터 저장 실패와 업로드 응답 불명확 오류는 새 파일 정리를 시도한다. 기존 경로 충돌(409)은 기존 파일을 지우지 않는다. 정리 실패 시 `PhotoError.pendingPhoto`에 다시 정리할 ID·경로를 보존한다.
- 사진 삭제는 본인 메타데이터를 조회해 파일을 먼저 지운 뒤 행을 지운다. 파일 삭제 실패 시 행은 유지한다. 삭제한 사진을 참조하던 레시피는 FK로 사진 ID만 null이 된다. T-50 편집 화면은 새 사진 업로드 → 레시피·재료 저장 → 이전 사진 정리 순서로 교체한다. 저장 실패 시 입력값과 업로드 ID를 유지하며 재시도에서 업로드를 재사용한다. 저장 성공 후 정리만 실패하면 편집을 잠그고 정리만 다시 시도한다. 취소 시 서버 저장 여부를 확인한 후 미저장 업로드만 지워 응답 유실로 이미 연결된 새 사진을 지우지 않는다. 레시피 삭제는 사진 파일·메타데이터를 먼저 지운 뒤 레시피를 지운다. 처리 중에는 중복 실행·편집·앱의 뒤로/취소 버튼을 잠근다. 탭 강제 종료·브라우저 이동 후의 자동 재정리 큐는 제공하지 않는다.
- `useRecipePhoto`는 공개 URL 대신 1시간 서명 URL을 50분마다 갱신하며 로그아웃 시 공통 Query 캐시와 함께 비운다. 서명 URL은 토큰을 가진 사람이 만료까지 읽을 수 있으므로 로그·백업에 넣지 않는다.
- 사진 교체·삭제·레시피 삭제 시 Storage 파일을 먼저 지우고 DB 행을 지운다. 파일 삭제에 실패해 남는 파일은 전체 삭제 시 함께 정리된다.

| 코드 요청 | `signInWithOtp({ email, options: { shouldCreateUser: false } })` |
| 코드 확인 | `verifyOtp({ email, token, type: 'email' })` |
| 메일 템플릿 | 대시보드의 **Magic link or OTP** 템플릿에 `{{ .Token }}`을 넣어 코드가 보이게 수정. **템플릿은 외부 메일(Custom SMTP)을 연결해야 수정할 수 있다** (C1 확인 완료) |
| 메일 발송 | Gmail SMTP (`smtp.gmail.com:587`). 앱 전용 발송 Gmail 계정을 쓰고, 그 계정의 앱 비밀번호는 Supabase SMTP 설정에만 저장한다 (저장소·환경변수에 넣지 않음) |
| 코드 길이 | **6자리** (Supabase 기본값 8자리에서 변경, Email OTP Length) |
| 코드 유효 시간·재발송 제한 | 기본 유효 시간 1시간을 **10분(600초)**으로 줄임. 같은 사용자의 재요청은 60초 간격(기본값). 코드 검증은 IP당 5분에 30회까지 (C2 확인 완료). 유효 시간 설정은 초대·이메일 변경 링크에도 함께 적용됨 |
| 세션 저장 | supabase-js 기본값(브라우저 localStorage) |

### 7.2 허용 이메일 관리

- dev, prod 프로젝트마다 대시보드에서 사용자 1명을 미리 등록한다. 이 목록이 곧 허용 이메일이다.
- 등록되지 않은 이메일은 `shouldCreateUser: false` 때문에 코드가 발송되지 않는다. 화면은 오류 응답을 받아도 같은 문구를 표시한다 (FR-AUTH-02).
- 기본 메일 발송 서비스는 **프로젝트당 시간당 2통**까지만 보내고 템플릿도 수정할 수 없어, Gmail SMTP를 연결했다 (C3 확인 완료). 외부 메일을 연결한 뒤에는 Authentication → Rate Limits에서 발송 한도를 정할 수 있다. 자동 테스트는 이메일을 쓰지 않는 방식(9.3~9.4)으로 한다.

## 8. 서버 로직 (DB 함수)

### 8.1 공통

| 함수 | 역할 | 관련 요구사항 |
| --- | --- | --- |
| `export_backup()` | 본인 데이터 전체(성장·식사 기록)를 JSON 1개로 반환. `schema_version`, `exported_at` 포함. 레시피 사진은 경로만 넣고 파일은 제외 | FR-SET-02, FR-SET-09 |
| `import_backup(payload jsonb)` | 버전·형식·필수값 검사 → 본인 데이터 전체 삭제 → 파일 내용 입력. 한 트랜잭션이라 중간에 실패하면 모두 취소됨 | FR-SET-03~05, R23 |
| `delete_all_data()` | 본인의 모든 테이블 데이터 삭제 (아이 정보 포함). 로그인 계정은 남김 | FR-SET-06~07 |

- `schema_version`은 정수로 시작한다 (MVP-1 = 1). 마이그레이션으로 백업 형식이 바뀌면 올린다.
- 백업 v1은 `{schema_version:1, exported_at, source_owner_id, data}`이며 data에는 `children`, `body_measures`, `milestones`, `sleep_logs`, `foods`, `photos`, `recipes`, `recipe_ingredients`, `meal_entries`, `meal_entry_foods`, `meal_entry_recipes`, `food_status_history` 배열을 모두 포함한다. 행의 owner_id와 자동 생성 name_key/title_key는 내보내지 않는다. 알려지지 않은 테이블·컬럼, 필수 키 누락, JSON 타입 오류, 중복 ID, 파일 밖 참조는 거부한다. 가져올 때 소유자는 항상 auth.uid()로 강제하며 행에 owner_id를 넣은 파일은 잘못된 형식으로 거부한다.
- `export_backup()`은 한 SELECT에서 모든 테이블을 읽는다. `import_backup()`은 같은 사용자 식단 advisory lock 후 대상 테이블을 EXCLUSIVE로 잠그고 검사·본인 행 삭제·재삽입을 한 트랜잭션으로 처리한다. 복원 중 다른 쓰기는 잠시 대기할 수 있다. 내부 오류는 원본 값을 노출하지 않는 backup_invalid로 바꾸며 예외 블록 전체가 롤백된다. 익명 실행을 막고 security definer·빈 search_path·본인 owner_id 범위를 적용한다.
- 원래 UUID와 created_at/updated_at·이름 스냅샷·순서·이력을 보존한다. 다른 계정 ID와 충돌할 때만 UUID를 다시 발급하고 모든 연결을 함께 바꾼다. 참조 대상은 같은 파일 안에 있어야 하며 타인 행을 연결하지 않는다. 기존 아이 생년월일 수정 후 남아 있는 과거 기록도 복원하기 위해 아이 정보는 마지막에 넣는다. 트리거를 끄지 않으며 일반 입력의 생년월일 검증 정책은 그대로다.
- 사진 경로는 출처 계정/사진 UUID.jpg 형식만 받고 현재 계정/복원된 사진 UUID.jpg로 바꾼다. Storage 파일을 복사·삭제하지 않는다. 동일 계정에서 파일이 남아 있으면 다시 연결되며, 다른 계정 또는 파일을 지운 뒤 복원하면 사진 없음으로 표시한다. JSON에 파일 바이트·서명 URL·인증 토큰은 들어가지 않는다.
- 화면과 DB에서 형식·버전을 검사한다. 파일은 10MiB, 전체 항목은 20,000개까지 허용한다. `backupSchema.ts`와 순수 `backupValidation.ts`를 API와 통합 테스트가 공유한다. `BackupSection`은 파일 검사·내용 요약·전체 교체 확인을 제공하며 취소는 RPC를 호출하지 않는다. 성공하면 모든 Query 캐시를 지우고 홈/등록으로 이동한다. 네트워크 오류는 완료 여부가 확실하지 않을 수 있어 입력 파일을 유지하고 재확인 후 재시도하며, 서버 검사 실패는 기존 데이터를 보존한다.
- `20261113020000_backup_export_import.sql`과 `20261113030000_backup_import_batch_validation.sql`을 순서대로 dev DB에 적용하고 DB 타입을 생성했다. 후속 마이그레이션은 JSON 타입·필수 키·ID 충돌·연결 재매핑을 테이블별 집계로 처리해 행마다 SQL·JSON 누적 복사를 반복하지 않게 하며 낮잠 내부 키·타입도 검사한다. 가명 화면 캡처 `docs/examples/backup-example-photo.png`를 사진으로 사용해 동일 계정 복원과 사진 파일 누락 대체 화면을 확인한다.
- 전체 삭제 시 Storage 사진도 지워야 한다. Storage 파일은 SQL로 직접 지우지 않고, 화면에서 본인 폴더(`{owner_id}/`)의 파일을 Storage API로 지운 뒤 `delete_all_data()`를 호출한다.

### 8.2 식사 기록

**레시피 저장(T-50)**: `save_recipe(id, name, ingredients, steps, servings, note, photo_id, create_new)`는 로그인 사용자의 레시피·재료를 일괄 저장한다. `id`는 폼 시작 시 생성해 재시도에서도 유지한다. 신규 입력만 `create_new=true`로 호출하며 기존 레시피가 삭제된 수정 요청은 P0002다. 같은 ID에 advisory lock을 걸고 기존 레시피를 FOR NO KEY UPDATE로 잠가 존재 확인 뒤 삭제되는 경합을 막으며, 타인 ID 수정을 거부한다. 마이그레이션 `20261113000000_save_recipe.sql`, `20261113010000_lock_recipe_edit.sql` 순서로 dev에 적용했다. 재료는 1개 이상인 객체 배열이며 이름·양·조리 순서·사진 소유권을 DB 제약과 함께 검사한다. 연결한 음식의 현재 이름을 저장하며 음식 목록 상태·첫 시도·먹은 횟수는 바꾸지 않는다. 어떤 재료라도 실패하면 레시피와 기존 재료 교체를 모두 롤백한다. `security definer`, 빈 `search_path`, `auth.uid()` 소유권 제한을 적용하며 실행 권한은 authenticated에만 준다. 기존 테이블의 RLS 직접 쓰기는 유지되므로 일괄 저장·재료 최소 개수 보장은 이 RPC 경로에 적용된다.

**레시피 화면(T-49·T-50)**: `/meals/recipes`는 이름순 목록·검색과 음식 ID 기반 AND 재료 필터를 제공한다. 검색 `q`, 선택 재료 `ingredients`를 URL에 보존해 상세에서 돌아와도 유지한다. 상세는 재료·양·주의·번호가 붙은 조리 순서를 표시한다. `/meals/recipes/new`, `/meals/recipes/:id/edit`은 식사 탭 틀 밖의 `FormPage`로 열며 모바일 하단 메뉴를 숨긴다. 재료 직접 입력은 음식 목록에 추가하지 않는다. 재료·조리 순서는 각각 한 Textarea에서 편집하고 `recipeText.ts` 순수 함수로 배열을 만든다. 재료는 한 줄씩 구분하고 숫자/단위·자유 양 표현 또는 명시적 `|`로 이름·양을 나눈다. 조리 글에 번호가 있으면 다음 번호까지 묶고 없으면 줄마다 구분한다. 빈 줄·글머리·굵게 표시를 정리하고 미리보기에서 1~N 번호를 붙인다. 기존 배열을 편집용 텍스트로 변환할 때 단계 내 줄바꿈과 자유 양을 보존한다. 같은 재료 이름·동일 이름의 등장 순서로 음식 ID를 연결해 줄 재정렬·양 변경 시 유지하며 이름이 달라지면 연결하지 않는다. 사용자가 미리보기의 음식 검색으로 연결을 선택·해제할 수 있다. 입력 중 원문을 다시 쓰지 않아 Enter·붙여넣기·IME 조합을 방해하지 않는다. 스키마는 파싱 후 재료/단계 최소 개수와 재료 이름 20자·양 20자를 검사하며 기존 RPC에 같은 배열을 전달한다. DB 변경은 없다.

**식사 연동(T-51)**: `useMealRecipes`는 `useRecipes`의 동일 캐시에서 음식 ID가 있는 재료 목록을 `MealRecipeOption`으로 변환한다. 식단 입력·표 먹음 체크·복사는 음식과 레시피 조회가 성공하고 재조회 중이 아닐 때만 경고 확인 후 실행한다. 레시피 조회 실패는 실제 0건과 구분하며 입력값을 보존하고 다시 시도한다. 삭제된 ID의 저장 실패(staleItem) 시 음식·레시피 캐시를 모두 무효화한다. 레시피 재료는 경고 계산에만 사용하며 식단의 직접 음식 배열에 넣지 않는다.

홈은 `useMealDay(today)`로 날짜 양 끝이 같은 식단을 읽고, 주간 캐시와 겹치지 않게 `['meals', 'day', today]` 키를 사용한다. 아침/점심/저녁/간식 순서로 이름 스냅샷·계획/먹음을 표시하고 해당 ID의 수정 시트로 연결한다. 빠른 기록의 식단은 `?date=today`로 주간 화면의 오늘 카드에 진입한다.

타임라인은 `useFoods`의 `firstTriedDate`가 있는 음식마다 `food-<id>` 항목을 계산해 날짜 최신순·월별로 합친다. 별도 타임라인 행은 저장하지 않으며 `types=food` 필터와 음식 상세 주소를 사용한다. 식단 추가/체크/이동/복사/삭제와 음식 수정 시 기존 음식 캐시 무효화로 날짜 변경·제거가 반영된다. 처음 먹은 날짜를 모르는 음식은 항목을 만들지 않는다. 서버의 실제 첫 시도 반환 목록만 전체 알림 문구로 표시한다. 타임라인의 좁은 PC 폭은 필터를 위로 배치하고, 가로 한 줄 행은 1,280px 이상에서 사용해 새 음식 배지·이름으로 인한 넘침을 막는다. 기존 `mealApi`·음식 RLS를 재사용하며 DB 변경은 없다.

| `clear_caution_tag(food_id, reason)` | "주의" 태그 해제 + 이력(먹어봄 → 먹어봄). 알러지·주의 정보와 지정한 날은 지우고 이력에 옮겨 적음. 태그가 없으면 22023 | FR-FOOD-13, R49 |

**식단 함수 입력·반환 계약 (T-40)**

- `save_meal_entry`: `id`를 생략하면 추가, 있으면 해당 칸 수정. `date`·`meal_type`은 필수이며, `eaten` 기본값은 false다. `foods`·`recipes`는 JSON 배열이며 둘을 합해 1개 이상 있어야 한다(22023).
- `foods`: `[{"food_id": "UUID", "food_name": "이름"}]`. 연결된 음식의 이름은 서버가 본인 음식 테이블에서 가져오므로 이름은 생략할 수 있다. ID가 null이면 삭제 전에 남은 이름이 필수다. 다른 계정·없는 음식 ID는 23503. 배열 순서가 `position`이다.
- `recipes`: `[{"recipe_id": "UUID 또는 null", "recipe_name": "이름"}]`. T-47부터 연결된 레시피는 본인 ID인지 확인하고 현재 이름으로 저장한다. 타인·없는 ID는 23503이며 삭제되어 ID가 null인 항목은 이름을 보존한다. 레시피 재료는 재계산 대상에 포함하지 않는다 (BR-15).
- 저장·먹음 체크·이동 결과: `{"id": "식단 UUID", "first_tried_foods": [{"id": "음식 UUID", "name": "음식 이름"}]}`. 기록 전 처음 먹은 날이 없고 직접 먹어봄으로 지정하지 않은 음식에 처음 날짜가 생길 때만 알림 목록에 넣는다. 기존 날짜의 변경이나 반복 저장은 재알림하지 않는다.
- `copy_meal_entry`: 로그인·본인 원본 검증 후 같은 사용자 식단 advisory lock과 원본 FOR SHARE 잠금 안에서 항목 순서·이름 스냅샷·메모를 읽는다. `save_meal_entry`를 새 ID·eaten=false·intake=null로 호출해 소유권·현재 이름·대상 충돌 검증을 재사용한다. 원본은 수정하지 않는다. 복사로 먹은 횟수·첫 시도 날짜·주의 이력이 늘어나지 않는다. 타인·없는 원본은 P0002, 비로그인은 42501, 대상/원본 칸 충돌은 23505다.
- T-53부터 식단 INSERT와 실제 날짜 변경에는 공통 생년월일 이전 검증을 적용한다(22007). 생년월일을 고친 뒤에도 기존 식단의 메모만 수정하는 동작은 막지 않는다.
- `delete_meal_entry`는 반환값이 없다. 본인 칸이 아니거나 없으면 다섯 함수 모두 P0002. 저장 오류가 나면 칸·내용·상태·이력 변경 전체가 취소된다.
- `move_meal_entry`: 네 인자는 모두 필수(null은 22023). ID·내용·연결 항목을 보존하고 날짜·끼니만 바꾼다. `uncheck=true`면 먹음을 해제하고, false면 기존 값을 유지한다(계획을 과거로 옮겨도 자동 체크하지 않음). 같은 칸으로 이동은 허용하고, 다른 기록이 있는 칸은 23505로 전체 취소한다. 먹음 상태의 미래 날짜는 서버에서 UTC 오늘 + 1일 기준으로 검사하고, 정확한 기기 날짜 확인·미래 이동 확인 창은 T-45 화면에서 처리한다. 처음 먹은 날과 주의 지정일 전후의 상태를 이동 후 다시 계산한다.
- 같은 사용자의 식단 함수는 트랜잭션 advisory lock으로 직렬화한다. 관련 음식 행은 ID 순으로 변경 전에 잠가 음식 수정·알러지 관리와 경합해도 같은 기준으로 재계산한다.
- `recalc_food`와 첫 시도 목록을 만드는 `recalc_meal_foods`는 내부 전용이며 authenticated·anon 모두 직접 실행할 수 없다.

**음식 상태 재계산 (내부 함수 `recalc_food`)**

1. `eaten_min` = 그 음식이 담긴 "먹음" 칸의 가장 이른 날짜
2. `first_tried_date` = `eaten_min`과 `manual_first_tried_date` 중 이른 날 (둘 다 없으면 null)
3. 상태 전환은 기능요구사항서 BR-11 표를 따른다.
   - 아직 안 먹어봄 → 먹어봄: "먹음" 기록이 생기면 (이력 없음)
   - 알러지·주의 → 먹어봄 + 주의 태그: `caution_since` 이후 날짜의 "먹음" 칸이 생기면 (이력: `meal_entry`)
   - 먹어봄 + 주의 태그 → 알러지·주의: `caution_since` 이후 날짜의 "먹음" 칸이 모두 없어지면 (이력: `revert`)
   - 먹어봄 → 아직 안 먹어봄: "먹음" 기록이 모두 없어지고 `manual_tried`도 false면 (이력 없음)
   - `update_food`로 "이미 먹어 봤어요"를 바꿀 때도 같은 규칙으로 다시 계산한다. 식단에 먹은 기록이 남아 있으면 직접 입력을 해제해도 먹어봄이다 (T-40)
   - `release_food_caution`의 "먹은 기록" 판단도 `recalc_food`를 쓴다 (T-40). 먹어봄 + 태그로 바뀔 때와 되돌릴 때는 알러지·주의 정보와 `caution_since`를 그대로 둔다 (T-38의 CHECK)
4. 식단 함수들은 한 트랜잭션 안에서 칸 저장과 재계산, 이력 기록을 함께 처리한다.

**함수 권한**

- 8.2 함수는 음식 상태 컬럼을 바꿔야 해서 `security definer`로 만든다 (D10). 함수 안에서 모든 조회·수정을 `owner_id = auth.uid()`로 제한하고 `search_path`를 고정한다 (6.2).
- 로그인한 사용자(authenticated)만 호출할 수 있게 anon의 실행 권한을 뺀다. 로그인하지 않은 호출은 42501로 거부된다.

## 9. 테스트 전략

### 9.1 단위 테스트 (Vitest)

- 대상: `src/domain/`의 순수 함수, Zod 검증 스키마
- 필수 케이스: 기능요구사항서 3.2의 생후 일수 예시 표 전체, BR-05 자정 처리(23:59 / 00:00 / 11:59 / 12:00 경계), BR-07 총 수면 시간, FR-SLEEP-07 오류 조건 각각, BR-03 같은 내용 판단, 주간 식단의 주 시작일(월요일) 계산

### 9.1.1 식사 DB 함수 통합 테스트 (Vitest + dev 프로젝트)

- 음식 상태 재계산은 DB 함수 안에 있으므로, dev 프로젝트의 테스트 계정으로 함수를 직접 호출해 결과를 확인한다.
- 필수 케이스: BR-11 상태 전환표의 모든 행, BR-12 재계산(칸 삭제·체크 해제·음식 제외·날짜 변경), BR-15 레시피는 상태 불변, BR-17 앱 사용 전 먹은 음식, D11 주의 태그 되돌림, 칸 이동 충돌, 미래 날짜 "먹음" 거부, 음식 이름 중복 거부

### 9.2 컴포넌트 테스트 (Vitest + Testing Library)

- 대상: 입력 폼의 검증 문구 표시, 빈 상태 화면(FR-COM-20), 확인 창 흐름

### 9.3 E2E 테스트 (Playwright)

- 대상: PRD 8장 MVP-1 완료 기준을 시나리오로 옮긴 것
- 실행 환경: dev 프로젝트, 가명 데이터
- 로그인 처리: 이메일 코드를 자동으로 받을 수 없으므로, dev 프로젝트의 테스트 계정 A로 **비밀번호 로그인**을 한 뒤 시나리오를 실행한다 (D3). 계정 정보는 로컬 PC의 `.env.test.local`에만 두고 CI에는 넣지 않는다. Secret key는 쓰지 않는다.
- 처음에는 로컬에서 수동 실행한다. CI 자동 실행은 MVP-1 완료 후 검토한다.

### 9.4 접근 제어 테스트

- dev 프로젝트에 테스트 계정 2개(A, B)를 두고 비밀번호로 로그인한다. A로 만든 데이터를 B가 조회·수정·삭제할 수 없는지, 로그인하지 않은 요청이 거부되는지 Vitest 통합 테스트로 확인한다.
- 새 테이블을 추가하는 PR에는 이 테스트를 함께 추가한다.

### 9.5 CI (GitHub Actions)

| 시점 | 실행 |
| --- | --- |
| PR 생성·갱신 | 린트, 타입 검사, 단위·컴포넌트 테스트, 빌드 |
| main 병합 | 위와 같음 (Cloudflare Pages 배포는 Pages가 따로 수행) |

- 저장소는 비공개(2026-10-21 변경)이며, GitHub Free 플랜의 비공개 저장소는 GitHub 호스트 러너를 **월 2,000분**까지 무료로 쓸 수 있다. CI 1회는 약 30초라 한도 안에서 충분하다.
- CI에는 Supabase 키를 넣지 않는다. 단위·컴포넌트 테스트는 Supabase에 연결하지 않고 실행되어야 한다.

## 10. 배포와 운영

### 10.1 배포

| 대상 | 방법 |
| --- | --- |
| 프론트엔드 | Cloudflare Pages를 GitHub 저장소에 연결. `main` 병합 시 자동 빌드·배포. 빌드 명령 `npm run build`, 결과 폴더 `dist` |
| 미리보기 배포 | 끈다 (E11). 미리보기도 prod Supabase를 바라보게 되기 때문 `[확인 C4]` |

### 10.2 보안 설정

- `.gitignore`에 `.env*.local`을 넣고, 커밋 전에 확인한다. 저장소가 비공개여도 협업자 추가나 공개 전환 가능성이 있으므로 비밀값을 커밋하지 않는 규칙은 그대로 지킨다.
- `public/_headers`로 기본 보안 헤더를 넣는다: 다른 사이트의 iframe 삽입 금지, MIME 추측 금지, Referrer 최소화. 콘텐츠 보안 정책(CSP)은 Supabase 주소만 허용하는 형태로 MVP-1 완료 후 적용한다.
- 브라우저 콘솔과 오류 메시지에 아이 정보(이름, 생년월일, 기록 내용)를 출력하지 않는다.
- GitHub Dependabot으로 의존성 보안 알림을 받는다.
